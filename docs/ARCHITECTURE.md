# RAGbase — How It All Works

A ground-up guide to the entire project: what it is, how data flows through it, and what
every important file does. Written assuming no prior knowledge of the codebase.

---

## 1. What RAGbase Is

RAGbase is a **local-first personal AI knowledge base**. You feed it documents — PDFs
(typed or handwritten), images, videos, YouTube links, plain text — and then chat with
all of them at once. Answers are generated by a local LLM and **grounded in your own
content with citations**, so you can see exactly which source and chunk every claim came
from. Nothing leaves your machine: inference, embeddings, vision, OCR, and storage all
run locally through [Ollama](https://ollama.ai) and embedded databases.

The technique behind it is **RAG (Retrieval-Augmented Generation)**: instead of asking
an LLM a question cold, the system first *retrieves* the most relevant snippets of your
documents, then hands those snippets to the LLM as context so the answer is anchored in
your actual notes rather than the model's general knowledge.

### The three machines/processes

| Component | Where it runs | What it does |
|---|---|---|
| **FastAPI backend** | your Mac, `localhost:8001` | All logic: ingestion, retrieval, generation, storage |
| **Next.js frontend** | your Mac, `localhost:3000` | Chat UI, source management, settings |
| **Telemetry server** | Raspberry Pi 5 (Tailscale `100.80.105.44`), Docker port 9000 | Receives anonymous usage events only — zero AI, zero user content |

There is **no Docker and no server processes** on the Mac beyond the two dev servers:
ChromaDB runs *embedded in-process* (a library, not a service), and the semantic cache
and knowledge graph are plain SQLite files under `data/`.

## 2. The Two Core Flows

Everything in the backend serves one of two flows: **ingestion** (getting a document in)
and **query** (getting an answer out).

### 2.1 Ingestion — two-phase, queued

```
upload → API saves file → job queued → [Phase 1: extract → chunk → embed → store → summarize]
                                              ↓ source is now queryable ("ingested")
                                       [Phase 2, background thread: build knowledge graph]
                                              ↓ job marked "done"
```

1. **Upload.** The frontend POSTs to `/ingest/file` (or `/url`, `/text`). The API saves
   the original file to `data/sources/{user_id}/` (so it can be previewed later), writes
   the bytes to a temp file, and enqueues a job. The response returns a `job_id`
   immediately — ingestion never blocks the HTTP request.

2. **Queue.** A single background worker thread (`ingestion/queue.py`) processes jobs
   one at a time, sequentially (a Mac can only run so many models at once). Job status
   moves through `queued → ingesting → ingested → building_graph → done`, persisted to
   `data/queue_status.json` so the frontend can poll `/ingest/status` and survive
   restarts.

3. **Phase 1 — extract, chunk, store** (`ingestion/base.py`). The right ingestor
   subclass extracts raw text (see per-format details below), splits it into
   overlapping ~512-word chunks, embeds each chunk with `bge-m3` (1024-dim vectors),
   and stores chunks + vectors + metadata in ChromaDB. It also asks the fast LLM for a
   3–4 sentence **document summary**, stored in a separate "summaries" collection —
   this powers the first stage of hierarchical retrieval. When Phase 1 finishes, the
   job is marked `ingested` and the source is **immediately queryable**. The semantic
   query cache is cleared (cached retrievals may now be stale).

4. **Phase 2 — knowledge graph** (background daemon thread). Each chunk is run through
   the fast LLM (`qwen2.5:3b`) to extract entities and relationships as JSON
   (`retrieval/graph.py`), which are inserted into per-user SQLite tables. This is slow
   and non-blocking — queries work fine before it finishes; the graph just adds
   cross-document linking once done.

**Per-format extraction:**

- **Typed PDFs** — Docling parses the document; text is grouped page-by-page and each
  page goes through a `TextCleanup` LLM pass (fixes spacing/encoding damage without
  changing content). Embedded images are rendered and described by the vision model,
  with descriptions spliced inline in place of `<!-- image -->` placeholders.
- **Handwritten PDFs** — detected when Docling returns mostly image placeholders with
  little text. Each page is converted to a PNG and *transcribed* by Qwen2.5-VL, with
  3 retries per page at escalating timeouts, progress saved to disk after every page
  (so a crash resumes mid-document), and a `TranscriptionRefinement` LLM pass that
  strips the model's narration ("It is mentioned that...") to keep only literal notation.
- **Images** — PaddleOCR extracts printed text *and* Qwen2.5-VL describes the visual
  content; a fast-LLM call fuses the two into one passage.
- **Video files** — Whisper transcription, formatted into timestamped paragraphs.
- **YouTube** — yt-dlp downloads the audio, then the same Whisper path.
- **Text/Markdown** — read directly.

### 2.2 Query — the RAG pipeline

When you ask a question, `/query/stream` runs this staged pipeline
(`retrieval/pipeline.py`), streaming progress events to the UI as each stage starts:

```
question
  │
  ├─ 0. Semantic cache check (non-streaming /query only)
  │
  ├─ 1. Stage-1 retrieval: search document SUMMARIES → which sources are even relevant?
  │       n_results scales with library size: min(max(3, total//3), 8)
  │       sources with cosine distance > 0.7 filtered out
  │
  ├─ 2. Knowledge graph augmentation: entities in the question seed a 2-hop
  │       NetworkX traversal → adds related sources stage 1 missed
  │
  ├─ 3. Chunk-level HYBRID search within those sources:
  │       vector search (bge-m3) + BM25 keyword scoring over the candidates,
  │       fused with Reciprocal Rank Fusion (k=60) → top ~20 candidates
  │
  ├─ 4. Cross-encoder rerank: BGE-Reranker-v2-m3 scores every (question, chunk)
  │       pair in one batched GPU forward pass → top 5
  │
  ├─ 5. Threshold filter: drop chunks scoring below -8.0. If NOTHING survives,
  │       the LLM answers from its own knowledge — no retry, no refusal.
  │
  └─ 6. Generation: qwen3 streams the answer token-by-token via SSE, with a strict
          system prompt forbidding it from narrating "the context" or citing
          source names inline. Citations arrive as a separate [SOURCES] event.
```

Why hybrid search? Vector search finds *semantically* similar text but can miss exact
keywords (error codes, names); BM25 is the opposite. RRF merges both rankings without
needing score calibration. Why a reranker? Bi-encoder retrieval (embeddings) is fast but
approximate; the cross-encoder reads the question and chunk *together* and is much more
accurate — so retrieval casts a wide net (20) and the reranker picks the best 5.

**The semantic cache** (`utils/cache.py`): query embeddings are compared against recent
past queries (cosine ≥ 0.85, 24h TTL, SQLite). On a hit, the expensive retrieval stages
are skipped and the cached *chunks* are reused — but the answer is always regenerated
fresh, because the new question is never exactly the old one.

**Direct mode**: if the user deselects all sources, `/query/direct` skips the entire
pipeline and streams a plain LLM answer — near-instant.

### 2.3 The SSE wire format

Streaming endpoints emit Server-Sent Events the frontend parses frame-by-frame:

```
data: {token}                                  ← answer text, token by token
data: [STAGE]{"stage": "retrieving_sources"}   ← progress ("traversing_graph", "reranking", "generating")
data: [SOURCES]{"sources": [...], "scores": [...], "chunks": [...]}
data: [HEARTBEAT]                              ← keep-alive during blocking stages
data: [DONE]
```

## 3. Identity, Settings, and Telemetry

- **User ID** — generated on first launch (`usr_` + 8 hex chars), stored in
  `data/user_id.txt`. **Clients never send a user_id**; every API handler reads the
  server-side constant. It exists to namespace storage (ChromaDB collections, graph
  tables, source folders) and to future-proof multi-user support.
- **Device ID** — a separate anonymous `dev_...` ID in `data/device_id.txt`, used
  *only* in telemetry payloads so usage metrics can't be linked to the user ID.
- **Settings** — `data/settings.json` holds runtime-mutable settings (telemetry on/off,
  display name), written atomically and loaded at startup. Static config lives in
  `config/settings.py` as plain constants — **there is no .env file**.
- **Telemetry** — fire-and-forget POSTs to the Pi (2s timeout, daemon thread, silently
  dropped if the Pi is unreachable). Events: `query_rag`, `query_direct`, `ingest`,
  `graph_complete` — carrying only latency, counts, and the device ID. Never queries,
  documents, or personal data. A settings toggle disables it entirely.

## 4. Backend File-by-File

### Entry point

**`main.py`** — Creates the FastAPI app. The `lifespan` context manager runs at startup:
loads `settings.json` overrides, logs the user/device IDs, configures DSPy to point at
Ollama, starts the ingestion queue worker, then kicks off two non-blocking warmup tasks
(the reranker model and each Ollama model) so first queries aren't cold. Registers all
API routers and the CORS middleware (any `localhost` port). `GET /health` lives here.

### `config/` — all constants and runtime state

- **`settings.py`** — Every tunable constant: `OLLAMA_URL`, `API_URL`, chunking
  (`CHUNK_SIZE=512`, `CHUNK_OVERLAP=50`), retrieval (`TOP_K_CANDIDATES=20`,
  `MAX_FINAL_RESULTS=5`, `RRF_K=60`, `RERANKER_MIN_SCORE=-8.0`), cache
  (`CACHE_TTL=86400`, `CACHE_SIMILARITY_THRESHOLD=0.85`), vision timeouts, handwriting
  detection thresholds, supported file extensions, `TELEMETRY_ENABLED` default.
- **`models.py`** — `get_model(task)`, the **single source of truth for model routing**.
  Every LLM call in the codebase asks this function which model to use (see §7). Nothing
  hardcodes a model name elsewhere.
- **`paths.py`** — Every file path: `DATA_DIR`, `CHROMADB_DIR`, `CACHE_DB_PATH`,
  `KNOWLEDGE_GRAPH_DB_PATH`, `USER_ID_PATH`, `DEVICE_ID_PATH`, `SETTINGS_JSON_PATH`,
  `SOURCES_DIR`, queue status, eval/training data paths.
- **`runtime.py`** — Runtime identity + mutable settings. Generates/reads `USER_ID` and
  `DEVICE_ID` at import time; manages the in-memory `settings.json` state with
  `is_telemetry_enabled()`, `set_telemetry_enabled()`, `get/set_display_name()`, all
  persisted with atomic writes (temp file + `os.replace`).
- **`logging.py`** — `setup_logging(name)`: console + per-module file handler under
  `logs/`. Used by every module; bare `print()` is banned.

### `api/` — FastAPI routers (thin HTTP layer; logic lives elsewhere)

- **`query.py`** — The three query endpoints. `POST /query` (complete JSON response;
  checks the semantic cache first), `POST /query/stream` (the main path — SSE with
  stage events, described in §2.2), `POST /query/direct` (no RAG). Owns the shared
  `_SYSTEM_PROMPT` that keeps qwen3 concise and stops it narrating its context. Sends
  query telemetry with latency and cache-hit flags.
- **`ingest.py`** — `POST /ingest/file|url|text` (save original + enqueue; URL ingest
  auto-fetches the YouTube title via yt-dlp and slugifies it; text ingest gets an
  LLM-generated title via `POST /ingest/generate_title`), `GET /ingest/status` (poll),
  `POST /ingest/clear_completed`, `POST /ingest/cancel/{job_id}`.
- **`documents.py`** — Source management: `GET /documents/` (list all sources with
  chunk/flag counts, aggregated from ChromaDB metadata), `GET /documents/{source}`
  (all chunks with fact-check/contradiction flags), `DELETE /documents/{source}`, and
  `POST .../check_facts` / `check_contradictions` triggers. ChromaDB calls are wrapped
  in `asyncio.to_thread` so they don't block the event loop.
- **`sources.py`** — `GET/HEAD /sources/{source}/file`: serves the stored original file
  (for PDF/image preview in the UI) with correct MIME types.
- **`settings.py`** — `GET /settings/user` (user_id + display name), `POST
  /settings/telemetry`, `POST /settings/display_name`.
- **`compact.py`** — `POST /compact`: summarizes old chat messages via the fast LLM for
  context-window management (the frontend calls this when a conversation nears the
  token limit).
- **`title.py`** — `POST /title`: 3–6 word chat title from the first message.
- **`sessions.py`** — `GET /sessions/should_reset`: one-shot flag consumed by the
  frontend after `reset_all.sh` runs, telling it to wipe localStorage chat history.
- **`__init__.py`** — exports all routers for `main.py`.

### `ingestion/` — getting documents in

- **`queue.py`** — The job queue. One daemon worker thread pulls jobs from a
  `queue.Queue` and instantiates the right ingestor per file extension (ingestors are
  imported lazily so heavy deps only load when needed). Status file helpers with atomic
  writes; startup reconciliation re-enqueues jobs that were mid-flight when the server
  died; duplicate detection refuses to enqueue a source that's already active;
  `cancel_job()`/`is_cancelled()` support cooperative cancellation; per-type
  `estimated_seconds` drive the frontend progress animation.
- **`base.py`** — `BaseIngestor` (ABC), the heart of ingestion. Subclasses implement
  *only* `extract_text()`; the base class owns the whole two-phase flow described in
  §2.1: `ingest()` orchestrates extract → chunk → (delete old data if re-ingesting) →
  `store()` (batched embedding + batched ChromaDB upserts, cancellation checks per
  batch, skips chunks whose embedding failed) → `store_summary()` → cache clear →
  telemetry → spawn the Phase-2 graph thread. `IngestionCancelled` is raised to unwind
  cleanly mid-run.
- **`pdf.py`** — `PdfIngestor`: handwriting detection, the resumable page-by-page VLM
  transcription loop with retry/timeout escalation, typed-PDF per-page extraction with
  the `TextCleanup` DSPy pass, and inline embedded-image description (§2.1).
- **`image.py`** — `ImageIngestor`: PaddleOCR (cached singleton, version-tolerant
  result parsing) + vision description + LLM fusion.
- **`video.py` / `youtube.py`** — Whisper transcription; youtube adds yt-dlp audio
  download and strict YouTube-domain URL validation.
- **`text.py`** — reads files directly; `ingest_string()` round-trips pasted text
  through a temp file to reuse the same pipeline.
- **`helpers.py`** — Shared utilities: `transcribe()` (Whisper + timestamped paragraph
  formatting), `describe_image()` and `vision_with_timeout()` (thread-based timeout —
  never `signal.alarm`, which only works on the main thread), and **`delete_source()`**
  — the one place that removes a source everywhere: chunks, summary, graph rows, and
  the query cache.

### `retrieval/` — getting answers out

- **`pipeline.py`** — The `RAGPipeline` DSPy module orchestrating §2.2. Key methods:
  `search_candidates()` (stages 1–3) and `rerank_candidates()` (stages 4–5) are split
  so the streaming endpoint can emit progress between them; `retrieve_context()` runs
  retrieval only, so the API can stream generation itself (DSPy's `Predict` can't
  stream). Also home to all DSPy signatures — `RAGAnswerer`, `TextCleanup`,
  `TranscriptionRefinement`, `QueryRewriter` (kept for ml/ scripts; not used in the
  live path — query rewriting was removed for costing 25–30s per query) — plus the
  prompt builders (`build_answer_prompt`, `build_direct_prompt`, `build_context`,
  `format_history`) and `configure_dspy()`.
- **`search.py`** — `search()`: the hybrid vector+BM25+RRF chunk search (§2.2 stage 3),
  with ChromaDB `where` filters for user isolation and source filtering (multi-field
  filters need explicit `$and`). `search_summaries()`: stage-1 document-level search
  with dynamic result count and the 0.7 distance cutoff.
- **`reranker.py`** — Loads BGE-Reranker-v2-m3 once (float32; MPS → CUDA → CPU
  auto-detect), scores all pairs in a single batched forward pass, falls back to a
  per-item loop if batching throws, and falls back to original order if the model
  can't load at all. Scores are raw logits, roughly −10..+8.
- **`embed.py`** — The **single import point** for `embed()`, `embed_batch()`, and
  `chunk_text()` (overlapping word-window chunking). Delegates to the Ollama client.
- **`graph.py`** — The knowledge graph. LLM entity/relationship extraction with heavy
  defenses: LaTeX stripped pre-extraction, `json_repair` before parsing (LLMs emit
  broken JSON), and validation that drops short/numeric/stop-word/duplicate entities.
  Storage is per-user SQLite tables (`nodes_{user_id}`, `edges_{user_id}`, WAL mode,
  30s timeouts because the graph thread and queue worker contend). Querying:
  `has_graph()` (cheap existence check so queries skip the graph when empty) and
  `query_related_sources()` — matches question words against node names, then walks
  ≤2 hops through a NetworkX digraph to find related sources.

### `analysis/` — optional content quality checks

- **`fact_check.py`** — Runs each chunk of a source past the fast LLM asking for clear
  factual errors; flags are written into the chunk's ChromaDB metadata and surface in
  the UI.
- **`contradiction.py`** — For each chunk, finds the 5 most semantically similar chunks
  from *other* sources and asks the LLM whether they contradict; flags both sides.
- **`common.py`** — Shared `parse_verdict()` (the `VERDICT:/REASON:` response format
  both checks use) and `update_chunk_metadata()` (merge fields into one chunk's
  metadata, located by source + chunk index).

### `utils/` — infrastructure clients

- **`ollama_client.py`** — Every Ollama call goes through here (except DSPy's own
  calls): `embed()`/`embed_batch()` (batch attempt with parallel per-item fallback, and
  shape-tolerant response parsing because ollama-python has changed response types
  across versions), `vision()` (base64 image chat with `num_ctx=8192` — Qwen2.5-VL
  truncates silently without it), `generate_stream()` (the token generator used for
  all streaming and most one-shot generation).
- **`chromadb_client.py`** — The embedded ChromaDB `PersistentClient` (singleton,
  persists to `data/chromadb/`, no server). Per-user collections: `user_{id}` for
  chunks, `user_{id}_summaries` for stage-1 summaries; cosine HNSW space. This is the
  *only* place user isolation is implemented.
- **`cache.py`** — The SQLite semantic cache (§2.2): embeddings stored as float32
  blobs, cosine similarity in numpy, per-user rows, TTL purge on read. Stores
  *retrieval context*, never answers.
- **`telemetry.py`** — `send_telemetry()`: checks the opt-out, then fire-and-forget
  POST to the Pi on a daemon thread. Payloads carry the device ID only.

### `ml/` — evaluation & training scripts (run via `python3 -m`, not part of the app)

- **`generate_eval.py`** — Generates eval questions from a source's chunks ("questions
  only answerable from this exact text"), appending to `data/eval_set.json`.
- **`eval.py`** — Retrieval quality benchmark: for each eval question, runs the real
  pipeline and measures top-k accuracy and MRR (did the correct chunk come back, and at
  what rank?). Logs to Weights & Biases.
- **`collect_pairs.py`** — Mines (question, positive chunk, negative chunk) training
  pairs from eval runs, for future reranker fine-tuning.
- **`finetune_embed.py`** — Future-use embedding fine-tuning with triplet loss.
- **`common.py`** — shared `to_chunk_index()` normalizer.

## 5. Frontend File-by-File

Next.js 16 (App Router) + TypeScript + Tailwind v4. Chat history lives in
**localStorage** — the backend is stateless about conversations; only documents and
settings persist server-side.

### `lib/` — the only place HTTP happens

- **`api.ts`** — Every backend call, fully typed. Notable pieces: the SSE parser
  (`consumeQueryStream`) that splits frames and dispatches `[STAGE]`/`[SOURCES]`/
  `[DONE]`/token events to handler callbacks, with `AbortController` support for the
  stop button; `streamQuery` / `streamDirectQuery`; ingestion calls (multipart forms);
  a module-level cache of `GET /settings/user` so the user identity is fetched once
  per session. **No `user_id` appears in any request** — the server knows it.
- **`config.ts`** — `DEFAULT_API_URL` only. The base URL can be overridden via
  localStorage from the settings page; nothing else in the codebase may reference
  `localhost:8001` directly.
- **`utils.ts`** — `cn()` (clsx + tailwind-merge class combiner) and
  `deriveSourceName()` (filename → source slug).

### `hooks/` — all stateful logic

- **`useChat.ts`** — The biggest hook: owns chat sessions (create/select/rename/pin/
  delete, persisted to localStorage), sends messages via `streamQuery` or
  `streamDirectQuery` (direct mode when zero sources are selected), accumulates
  streamed tokens into the growing assistant message, records per-message stage/
  latency/citations, auto-generates a session title from the first exchange, estimates
  token usage (chars/4 + overhead per exchange), and **auto-compacts**: past 90% of
  qwen3's 40,960-token window it sends older messages to `/compact` and replaces them
  with a summary message, keeping the last 10 intact. Also consumes the
  `should_reset` flag on startup.
- **`useIngestion.ts`** — Upload/ingest actions plus adaptive polling of
  `/ingest/status` (1s while queued, 2s while ingesting, 3s otherwise; stops when no
  jobs are active), job cancellation, and the 30-second fade-out of completed jobs.
- **`useSources.ts`** — Fetches the source list from `/documents/`, exposes
  refresh/delete.
- **`useSettings.ts`** — API URL (localStorage), display name and telemetry toggle
  (synced to the backend settings endpoints), and the fetched user ID.

### `app/` — pages

- **`page.tsx`** — The main three-panel layout: Sidebar (sessions) | ChatArea |
  SourcesPanel (ingestion + source filter). Wires the three hooks together.
- **`settings/page.tsx`** — Display name, API URL, the anonymous-telemetry toggle, and
  theme selection.
- **`layout.tsx` / `providers.tsx`** — Root HTML shell and the `next-themes` provider
  for dark/light mode.

### `components/`

- **`chat/ChatArea.tsx`** — messages list + input; **`MessageBubble.tsx`** — renders
  markdown with KaTeX math, copy button, latency/timestamp, and the "Sources used"
  button opening an inline chunks modal showing the exact cited text and scores;
  **`ChatInput.tsx`** — textarea with Enter-to-send and a stop button that aborts the
  stream mid-generation (partial answer is kept); **`SourceFilter.tsx`** — pick which
  sources a query may use (amber dot = graph still building); **`ModelSelector.tsx`** —
  qwen3 (+ "coming soon" placeholders).
- **`layout/Sidebar.tsx`** — session list with pin/rename/delete, the context-window
  usage bar (green→amber→red), and the display-name greeting; **`SourcesPanel.tsx`** —
  File/Text/YouTube ingestion tabs and the live job queue with progress animations
  driven by the backend's `estimated_seconds`; **`ThemeToggle.tsx`** — three-way
  light/system/dark switch (hydration-safe via a mounted gate).
- **`sources/DropZone.tsx`** — drag-and-drop upload; **`SourcesModal.tsx`** — card grid
  of all sources with previews; **`PDFPreview.tsx`/`PDFThumbnail.tsx`** — react-pdf
  rendering (CDN worker pinned to the installed pdfjs version; text/annotation layers
  disabled to avoid re-render loops).
- **`ui/ConfirmDialog.tsx`** — shared destructive-action confirmation.

### `types/index.ts`

All shared shapes: `SourceSummary`, `IngestionJob`/`IngestionStatus` (API responses),
and the app-local `Message` (role, content, citations, stage, latency, `type:
"summary"` for compaction messages), `ChatSession`, `CitedChunk`.

## 6. Scripts & Operations

| Script | Purpose |
|---|---|
| `scripts/install.sh` | First-time setup: OS + prerequisite checks (Ollama, Python 3.11+, Node 18+), pulls the four Ollama models, creates the uv venv and installs deps (pinning `huggingface-hub<1.0` — newer versions break transformers), `npm install`, creates data dirs |
| `scripts/start.sh` | Starts backend (`python3 -m uvicorn main:app --port 8001`) + frontend, waits for ready, opens the browser. Ctrl+C stops both |
| `scripts/reset_all.sh` | Full wipe: kills servers, deletes `data/chromadb/`, graph DB, cache DB, stored sources, logs, queue status; touches the reset flag so the frontend clears chat history |
| `scripts/status.sh` | Queue status + recent log tail |
| `scripts/metrics.sh` | SSHes to the Pi, pulls `/metrics`, prints cache-hit rates and latency breakdowns |
| `scripts/ingest_training_data.sh` | Batch-ingests every PDF in `data/training_data/` |

### `data/` layout (all gitignored)

```
data/
├── chromadb/            embedded vector store (chunks + summaries)
├── cache.db             SQLite semantic query cache
├── knowledge_graph.db   SQLite entity graph (per-user tables)
├── sources/{user_id}/   original uploaded files, for preview
├── queue_status.json    ingestion job states
├── user_id.txt          auto-generated usr_XXXXXXXX
├── device_id.txt        anonymous dev_XXXXXXXX for telemetry
└── settings.json        telemetry toggle + display name overrides
```

### The Pi telemetry server

`~/telemetry/` on the Pi: a ~80-line FastAPI app (`server.py`) in a Docker container.
`POST /telemetry` inserts `{event_type, device_id, metadata, timestamp}` into SQLite at
`/data/metrics.db`; `GET /metrics` returns aggregates (query counts, average latency,
ingest/graph counts) plus the recent event list `metrics.sh` uses for cache-hit
breakdowns. It never sees queries, documents, or the real user ID.

## 7. Model Stack

| Task | Model | Why |
|---|---|---|
| Answer generation | `qwen3` | Best local quality; verbose by default so a concise system prompt is always passed |
| Summaries, titles, cleanup, entity extraction, fact/contradiction checks | `qwen2.5:3b` | Fast, non-thinking — fine for mechanical tasks |
| Handwriting, diagrams, image description | `qwen2.5vl` | Vision-language; needs `num_ctx=8192` |
| Embeddings | `bge-m3` | 1024-dim, strong multilingual retrieval |
| Reranking | `BAAI/bge-reranker-v2-m3` (HuggingFace, not Ollama) | Cross-encoder, batched on MPS, warmed at startup |
| OCR (images) | PaddleOCR | Printed text |
| OCR (typed PDFs) | RapidOCR via Docling | Docling's built-in path |
| Speech | Whisper (base) | Video/YouTube transcription |

All routing goes through `config/models.py::get_model(task)` — swap a model in one place.

## 8. Key Design Decisions (the "why")

- **Embedded everything** — ChromaDB in-process and SQLite for cache/graph means zero
  Docker, zero services to manage, and trivial installation. The tradeoff (single
  process access) doesn't matter for a single-user local app.
- **Two-phase ingestion** — users can query a document seconds after upload; the slow
  graph build happens behind the scenes.
- **Cache chunks, not answers** — semantically similar questions reuse retrieval (the
  expensive part) but always get a freshly generated answer for their exact phrasing.
- **No query rewriting in the live path** — it cost 25–30s per query for marginal
  retrieval gains. The class remains for ml/ experiments.
- **Graceful degradation everywhere** — reranker fails → original order; vision times
  out → OCR only; graph missing → skip augmentation; no chunks pass threshold → LLM
  answers from its own knowledge. One broken component never takes down a query.
- **Server-owned identity** — clients never send `user_id`; the backend reads it from
  disk. Simpler API, no spoofable parameter, and telemetry uses a separate anonymous ID.
- **DSPy for signatures, raw streaming for answers** — DSPy structures the internal
  LLM passes (cleanup, refinement), but final answers stream straight from Ollama
  because DSPy's `Predict` can't emit tokens incrementally.
