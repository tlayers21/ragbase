## 1. Project Overview

RAGbase is a personal, local-first AI knowledge base: ingest notes, PDFs, images, videos, and
YouTube transcripts, then chat with all of it and get grounded answers with citations. It's built
as a portfolio project targeting ML/systems engineering roles, so the design choices favor
demonstrating a real, working retrieval-augmented-generation system end to end over minimizing
lines of code.

**Core architectural bet: everything runs on one Mac.** Ollama inference, ingestion pipelines,
the FastAPI backend, ChromaDB (embedded in-process, no server), and a SQLite knowledge graph +
cache all live on the same M3 Mac. A Raspberry Pi 5 exists purely as a telemetry sink — a small
FastAPI server writing to SQLite, reachable over Tailscale — and runs zero AI compute and zero RAG
logic. This means the Pi can go offline without affecting the app at all; it just stops recording
anonymous usage events.

**Why this matters for how the code reads:** because there's no distributed system to reason
about, most of the interesting complexity is concurrency *within* one process — a background
ingestion queue, a background graph-build queue, SQLite files written from multiple threads, and
an in-process reranker model competing for the same GPU/MPS device as Ollama. The `timeout=30`
convention on every SQLite connection and the deliberately *sequential* graph-build queue both
exist to tame that single-machine concurrency, not to coordinate across machines.

**The retrieval pipeline is hybrid and multi-stage**, not a single vector search: a cheap
document-summary pre-filter (Stage 1) narrows which sources are even worth searching, an
optional knowledge-graph traversal pulls in related sources, a hybrid BM25+vector search
(Stage 2) finds candidate chunks, a cross-encoder reranker re-scores them, and a semantic cache
sits in front of the whole thing. Each stage is a deliberate response to a specific weakness of
naive top-k vector search (see §3, Key Design Decisions).

**Frontend and backend are decoupled but co-located.** The Next.js frontend talks to FastAPI over
plain HTTP + SSE at `localhost:8001`; there's no shared process, no server components calling into
Python. All persistence that's cheap to keep client-side (chat sessions) lives in `localStorage`
rather than a database table, because it's genuinely simpler and there's exactly one user.

## 2. Module by Module

### `main.py` — FastAPI entry point

Owns the `lifespan` context manager: loads runtime settings, configures the global DSPy LM once
(`configure_dspy(OLLAMA_URL, MODEL_STANDARD)`), starts both background queue workers
(`start_ingestion_queue()`, `start_graph_queue()`), and kicks off two **non-blocking** warmup
tasks (`asyncio.create_task`, not awaited) for the reranker and four Ollama models
(`answer`, `summarize`, `embed`, `vision_simple`). Warmup failures are caught and logged as
warnings, never crash startup — the app is still usable, just slower on the first real request.

Non-obvious: the model-warmup loop calls the Ollama client functions directly
(`ollama.generate`, `ollama.embed`) rather than going through `utils/ollama_client.py`. This is a
deliberate, narrow exception to the "all Ollama calls through `ollama_client.py`" convention,
made explicitly for a one-shot startup ping — flagged in `.ai/instructions.md` as worth a second
look, since a future refactor of the client module wouldn't automatically cover this path.

CORS allows `http://localhost:3000` plus any `http://localhost:<port>` via `allow_origin_regex`,
because the Next.js dev server falls back to another port if 3000 is taken. This needs updating
before any real deployment.

### `config/` — all constants, one settings file

- **`settings.py`** — every tunable constant in the system (chunk size, thresholds, timeouts,
  supported file extensions). No `.env` file exists; this file *is* the config, with
  `data/settings.json` providing narrow runtime overrides (telemetry toggle, display name) via
  `config/runtime.py`. Hardcoded defaults are simpler to reason about for a single-user local app
  than an environment-variable layer that adds indirection nobody needs yet.
- **`models.py`** — `get_model(task)` is the single source of truth for model routing. It raises
  `ValueError` on an unknown task key rather than silently falling back, which is what makes model
  routing auditable: any string not in the routing dict fails loudly at call time instead of
  quietly resolving to the wrong model. Two task keys (`query_rewrite`, `vision_diagram`) are
  defined but not currently invoked anywhere in the codebase — harmless, kept for a task that
  isn't wired up yet rather than dead weight to delete.
- **`paths.py`** — every file path as a `pathlib.Path`, including the one-character difference
  that matters: `KNOWLEDGE_GRAPH_DB_PATH` is `data/knowledge_graph.db`, not the more obvious
  `graph.db`.
- **`runtime.py`** — generates `USER_ID`/`DEVICE_ID` on first launch (persisted to
  `data/user_id.txt`/`data/device_id.txt`), and reads/writes `data/settings.json` for the small
  set of runtime-overridable settings, using atomic writes (temp file + `os.replace()`) so a crash
  mid-write can't corrupt the settings file.
- **`logging.py`** — `setup_logging(name)`, the only sanctioned way to get a logger. Bare `print()`
  in production code paths is treated as a convention violation (the standalone `ml/` training
  scripts are a deliberate, narrower exception — see below).

### `ingestion/` — two-phase ingestion pipeline

The central design decision here is splitting ingestion into two phases so a source becomes
queryable **immediately**, without waiting for the slower knowledge-graph build:

**Phase 1** (`ingestion/base.py::BaseIngestor.ingest()`, synchronous, runs in the ingestion
queue's single worker thread): extract text → chunk → store in ChromaDB → generate a document
summary → mark the job `"ingested"`. At this point the source is fully searchable. Re-ingesting a
source that already has chunks wipes its prior chunks and graph data first, so re-ingestion is
idempotent rather than additive. `clear_cache(user_id)` runs after Phase 1 completes, because any
cached retrieval context computed before this ingestion is now stale.

**Phase 2** (background, `enqueue_graph_build()`): entity/relationship extraction into the
per-user SQLite knowledge graph, on a **separate, single-worker queue** distinct from the
ingestion queue. Job status moves `waiting_for_graph → building_graph → done`. This queue is
deliberately single-worker and separate from ingestion so that graph builds from several sources
ingested in quick succession don't pile up concurrent calls to `qwen2.5:3b` — they queue and run
one at a time instead.

Subclasses of `BaseIngestor` (`PdfIngestor`, `ImageIngestor`, `VideoIngestor`, `YoutubeIngestor`,
`TextIngestor`) implement only `extract_text()`; chunking, storage, and graph enqueueing are
handled once in the base class, which is the main mechanism keeping five different file-type
pipelines from duplicating logic.

Per-file notes:
- **`pdf.py`** — detects handwritten vs. typed PDFs via a heuristic (`_is_handwritten()`: many
  embedded images + little extracted text ⇒ handwritten). Handwritten PDFs go page-by-page through
  Qwen2.5-VL with progress-file resume and three retries at escalating timeouts, then a DSPy
  `TranscriptionRefinement` pass strips VLM narration ("The image shows...") using the fast model.
  Typed PDFs iterate `doc.texts` grouped by `.prov[0].page_no` — **never** `doc.pages`, which
  Docling populates with page metadata only, no text. **Known gap found in this audit**: the
  `DocumentConverter()` here is constructed with no `ocr_options=` at all, so OCR for typed PDFs
  actually runs on Docling's default engine (EasyOCR), not RapidOCR as the project's own docs
  previously (incorrectly) claimed — see `.ai/instructions.md`'s OCR table for the full note.
  This is flagged for a human decision, not silently patched.
- **`image.py`** — fuses PaddleOCR (printed text) with a Qwen2.5-VL visual description via an
  explicit `generate_stream(..., model=get_model("summarize"))` call — the two extraction paths
  get combined into one coherent passage only if both produced output; if only one did, it's used
  directly with no LLM call.
- **`video.py`** / **`youtube.py`** — both funnel through `helpers.transcribe()` (Whisper `"base"`
  on MPS when available, `fp16=False` always — Whisper's MPS fp16 path has known correctness
  issues). `youtube.py` validates URLs by exact domain match against a fixed set
  (`youtube.com`, `youtu.be`, `www.youtube.com`, `m.youtube.com`, `music.youtube.com`), not a
  substring check — an unlisted subdomain is rejected even though it "contains" youtube.com,
  which is the safer failure mode for URL validation.
- **`text.py`** — the only ingestor with a second entry point, `ingest_string()`, for raw pasted
  text: it writes a temp file and delegates to the normal path rather than duplicating the
  extract/chunk/store logic.
- **`queue.py`** — the two single-worker queues described above, plus **startup reconciliation**:
  any job left in an active status (e.g. the process was killed mid-ingest) is reset to `"queued"`
  and re-enqueued on restart, provided its status-file entry still has `source`, `user_id`, and
  `tmp_path`; otherwise it's dropped with a warning, since there's no way to resume it safely.
  Duplicate detection prevents enqueueing a second job for a source+user pair that already has an
  active job.
- **`helpers.py`** — `vision_with_timeout()` uses `ThreadPoolExecutor`, deliberately never
  `signal.alarm()` (signal-based timeouts don't compose well with threads). `delete_source()`
  lives here as a standalone function rather than a method on the ingestor classes, so deletion
  works without an ingestor instance around — it removes chunks, the summary, graph data, and
  clears the cache in one place.

### `retrieval/` — the hybrid RAG pipeline

Six logical stages, implemented in `retrieval/pipeline.py::RAGPipeline`:

1. **Stage 1 — summary search** (`search_summaries()` in `retrieval/search.py`): searches the
   `user_{id}_summaries` ChromaDB collection (one short LLM-generated summary per source, not per
   chunk) to cheaply narrow which *sources* are worth searching at all, before paying the cost of
   full hybrid search. `n_results` scales with corpus size
   (`min(max(3, total_sources // 3), 8)`), and results with cosine distance above
   `SUMMARY_DISTANCE_THRESHOLD` (0.7) are filtered out as likely off-topic — but if *everything*
   exceeds the threshold, the filter is dropped rather than returning zero sources, since an
   empty result set is a worse failure mode than a slightly-off-topic one.
2. **Graph augmentation** — `query_related_sources()` does a NetworkX BFS (2 hops by default) over
   the per-user knowledge graph to pull in sources connected to the Stage 1 results but not
   directly matched by the summary search. Gated by `has_graph(user_id)` so this is skipped
   entirely (no wasted SQLite round-trip) for users who haven't ingested enough to build a graph.
3. **Stage 2 — hybrid search**: vector search finds `TOP_K_CANDIDATES` (20) candidates, then BM25
   *rescoring* runs only over that candidate pool — not the full corpus — combined via
   Reciprocal Rank Fusion (`RRF_K=60`). Rescoring only the vector-search pool rather than
   independently searching the full corpus with BM25 is a deliberate cost/quality tradeoff: much
   cheaper, and BM25 over an already-relevant candidate set still meaningfully re-ranks for
   exact-term matches embeddings miss.
4. **Reranking** (`retrieval/reranker.py`) — `BAAI/bge-reranker-v2-m3`, loaded fresh from
   HuggingFace on every run (no fine-tuned local checkpoint currently — `RERANKER_MODEL_PATH`
   exists in `config/paths.py` defensively, for if/when one is trained), batched into a single
   forward pass across all candidate pairs rather than one call per pair, with a per-item fallback
   loop if the batch call raises, and a final fallback to original ranking (score 1.0 for
   everything) if the model fails to load at all — reranking degrades the *quality* of results
   under failure, never crashes the query. Chunks scoring below `RERANKER_MIN_SCORE` (-8.0, an
   empirically-tuned cutoff on the model's unbounded raw logits) are dropped.
5. **Cache check** (`utils/cache.py`) — a SQLite-backed semantic cache keyed on embedding cosine
   similarity (`CACHE_SIMILARITY_THRESHOLD=0.85`, 24h TTL). Critically, it caches *retrieval
   context only*, not the generated answer — a cache hit still regenerates the answer fresh
   against the *current* question, so near-duplicate questions get fresh wording without
   re-running the expensive retrieval stages.
6. **Generation** — the `RAGAnswerer` DSPy signature (`dspy.Predict`, not `ChainOfThought`) runs on
   `qwen3` with a deliberately concise system prompt, because Qwen3 is verbose and prone to
   narrating its own retrieved context by default. If no chunks survive the reranker threshold,
   the LLM answers from its own knowledge rather than refusing — a fallback-friendly design choice
   over a strict "only answer from sources" policy.

`search_candidates()` (stages 1–3) and `rerank_candidates()` (stage 4) are exposed as separate
methods specifically so `api/query.py`'s streaming endpoints can emit `[STAGE]` SSE events between
them, giving the frontend real progress feedback instead of one long silent wait.

DSPy signatures live **only** in `pipeline.py` — `QueryRewriter`, `RAGAnswerer`, `TextCleanup`,
`TranscriptionRefinement`, all `dspy.Predict`. `QueryRewriter` is kept even though `forward()`
doesn't call it (query rewriting was removed for latency — see §3) because `ml/eval.py` and
`ml/collect_pairs.py` still call `pipeline.rewriter` directly to reproduce the retrieval path when
generating training/eval data.

`retrieval/graph.py` — entity extraction routes through `get_model("entity_extraction")`, a
dedicated task key (mapped to the same fast model as `"summarize"`, but semantically its own key
rather than borrowing an unrelated one). `json-repair` runs before `json.loads()` on the LLM's
JSON output, since malformed JSON from a 3B model is common enough to need defensive parsing
rather than a bare `try/except` that drops the whole extraction. Entity/table names are validated
against `^[A-Za-z0-9_]+$` before being interpolated into SQL — this is the one place in the
codebase where a value derived from user-controlled input (`user_id`) is used to build a table
name, so this exact validation is what prevents SQL injection there.

### `analysis/` — fact-checking and contradiction detection

`fact_check.py` and `contradiction.py` are structurally identical: build a prompt, call
`generate_stream(prompt, model=get_model("fact_check"|"contradiction"))`, parse a
`VERDICT: .../REASON: ...` response via the shared `parse_verdict()` in `common.py`. Both default
to the "safe" verdict (not flagged / no contradiction) if the LLM response doesn't parse cleanly,
so a malformed response can never *incorrectly* flag content — it can only fail to flag something
that should have been. `update_chunk_metadata()` writes results back into ChromaDB metadata by
`(source, chunk_index)` and never raises on failure, since one metadata write failing shouldn't
abort a whole analysis run over many chunks.

### `api/` — FastAPI routes

Eight routers registered in `main.py` (`ingest`, `query`, `documents`, `sources`, `sessions`,
`title`, `compact`, `settings`), none of which accept `user_id` in the request — every route reads
it from `config/runtime.py`'s module-level `USER_ID`, since this is a single-user local app and
threading a `user_id` through every request would be pure ceremony.

`query.py` is the largest file: `POST /query` (complete JSON), `POST /query/stream` (SSE with
`[STAGE]` events), `POST /query/direct` (bypasses RAG entirely — used when the user deselects all
sources, going straight to `qwen3`), and `POST /query/with_attachments` (multipart, images through
`describe_image()`, PDFs through a one-shot PyMuPDF extraction — deliberately *not* the same
Docling path ingestion uses, since attachments need to be fast and are never persisted).
Attachments are never chunked or embedded; their extracted text/description is prepended to the
question string for that turn only, and the frontend re-sends it as part of `history` on later
turns rather than the backend storing it anywhere. All three streaming routes check
`await request.is_disconnected()` before each expensive blocking step, so clicking "Stop" in the
UI actually halts backend work rather than just hiding the stream client-side. Every SSE endpoint
emits `[HEARTBEAT]` during blocking calls — including once per attachment in
`/query/with_attachments`, since a multi-attachment request with several 30-50s vision calls could
otherwise leave the connection silent long enough to trip a proxy timeout.

`documents.py` wraps every ChromaDB call in `asyncio.to_thread()`, since the ChromaDB client is
synchronous and would otherwise block the event loop.

### `frontend/` — Next.js 16 App Router

A three-panel layout (`app/page.tsx`: Sidebar | ChatArea | SourcesPanel) with all shared types in
`types/index.ts` and all API calls funneled through `lib/api.ts` — no component or hook calls
`fetch` directly, which is what makes it possible to reason about every network call from one
file. `consumeQueryStream()` is the single SSE parser shared by all three streaming query
functions, so a new SSE event type only needs to be handled in one place.

State is React hooks only — no Redux/Zustand. Chat state is genuinely multi-session
(`useChat` holds a `ChatSession[]`, not one conversation), persisted to `localStorage`, which is
what lets the app skip a backend chat-history table entirely: the browser already does this well
for a single local user, and there's no cross-device sync requirement to justify a server-side
store.

Notable gotchas baked into the component code (see `.ai/skills/frontend.md` for the full list):
react-pdf's `options` prop must be a memoized object (`useMemo`) or it triggers an infinite
re-render loop; the CDN worker URL must match the exact installed `pdfjs-dist` version; the focus
ring lives only on the chat input's outer container, never on inner elements.

### `ml/` — evaluation and (future) training scripts

`eval.py` reproduces the real retrieval path (via `pipeline.rewriter` + `pipeline._retrieve()`) to
log top-k accuracy/MRR to Weights & Biases — using the actual pipeline code rather than a
reimplementation is what keeps this eval honest as the pipeline evolves. `collect_pairs.py` and
`finetune_embed.py` are explicitly "future use" — reranker training-pair collection and embedding
fine-tuning aren't wired into any live path yet. These two files (plus `generate_eval.py`'s CLI
entry point) use bare `print()` for user-facing script output rather than the logging convention
that applies to the live pipeline — a deliberate, narrow exception for standalone CLI tools whose
whole job is printing progress to a human running them directly, not writing to structured logs.

### `utils/` — shared infrastructure

- **`chromadb_client.py`** — `PersistentClient(path="data/chromadb/")`, embedded, no server. Two
  collections per user: `user_{id}` (chunks) and `user_{id}_summaries` (note: plural suffix,
  a naming detail easy to get wrong from memory).
- **`ollama_client.py`** — the single point of contact with Ollama for everything except DSPy's
  own internal LM calls. `embed()`/`embed_batch()` use the current `ollama.embed()` API (this
  audit corrected a prior use of the deprecated `ollama.embeddings()`), with response-shape
  extractors tolerant of multiple ollama-python response formats — defensive code written because
  that shape has changed across library versions before. `generate_stream()` wraps `ollama.chat()`
  (not `generate()` — conversation is built as a messages list) and defaults to
  `get_model("answer")` when the caller omits `model=`; in the current codebase only
  `ml/generate_eval.py` relies on that default, every other call site passes `model=` explicitly.
- **`cache.py`** — SQLite in WAL mode, replacing what would otherwise be a Redis dependency; for a
  single-process local app, SQLite avoids a whole extra service to run and monitor.
- **`telemetry.py`** — fire-and-forget POST to the Pi, on a daemon thread so a slow/unreachable Pi
  never blocks a request. Sends `device_id`, never `user_id` or content, and checks
  `is_telemetry_enabled()` before sending anything.

### `scripts/`

`install.sh` (first-time setup), `start.sh` (checks for upstream updates, rebuilds the frontend
only if its source hash changed, starts both servers, opens the browser), `reset_all.sh` (full
data wipe — chromadb, knowledge graph, cache, queue status, eval/training artifacts, sources —
plus a one-shot flag file so the frontend clears its `localStorage` chat sessions on next load).

## 3. Key Design Decisions

**Embedded ChromaDB over a ChromaDB server.** No Docker, no separate process to keep alive, no
network hop for what's fundamentally a local, single-user vector store. The tradeoff is no
multi-process access to the same collection — fine here, since only the one FastAPI process ever
touches it.

**SQLite for both the cache and the knowledge graph, not Redis/Postgres.** Same reasoning as
ChromaDB: one less service, cross-platform by default, and the write volume (per-query cache
writes, per-ingestion graph writes) is nowhere near what would require a dedicated database
server. `timeout=30` on every connection is the concession this choice requires — SQLite's
file-level locking means the ingestion queue's writer thread and the graph queue's writer thread
(plus any concurrent API read) can genuinely contend, and a short timeout would surface as
spurious "database is locked" errors under normal concurrent use.

**A dedicated, single-worker graph-build queue, separate from ingestion.** Graph building is the
one part of ingestion that's both slow (many LLM calls for entity extraction) and safe to fully
serialize, since nothing downstream blocks on it (a source is already queryable after Phase 1).
Making it strictly sequential across *all* sources — not just per-source — is what prevents
several fast Phase-1 completions from firing off concurrent graph builds that would otherwise
saturate `qwen2.5:3b` with parallel requests it can't serve well.

**Two-phase ingestion.** The alternative — block until the graph is built before marking a source
queryable — would make ingestion latency dominated by the slowest part of the pipeline instead of
the fastest useful part. Splitting phases means a user can start asking questions about a document
seconds after upload instead of minutes.

**No query rewriting in the live path**, despite `QueryRewriter` still existing as a DSPy
signature. It was measured to add 25-30 seconds of latency for minimal retrieval-quality benefit
and was cut from `forward()` — but kept in the codebase (and still exercised by `ml/eval.py`) both
as a documented decision (rather than a silent deletion someone might "helpfully" re-add without
knowing why) and because the eval/training scripts need it to reproduce the retrieval path
faithfully.

**DSPy for the LLM-facing logic**, rather than hand-rolled prompt strings for every task. DSPy
signatures give a typed contract (`Predict`) around what would otherwise be ad hoc string
templates, and centralizing all signatures in one file (`pipeline.py`) makes "what LLM calls exist
in this system and what do they promise to return" a one-file question rather than a repo-wide
grep.

**A cross-encoder reranker as a distinct stage from vector search**, rather than trusting
embedding-similarity ranking alone. Bi-encoder (embedding) similarity is fast but coarse; a
cross-encoder reranker sees the query and each candidate chunk together and produces a much better
relevance signal — expensive per-pair, which is exactly why it only runs over the already-narrowed
candidate pool from Stage 2, not the whole corpus.

**LLM-as-fallback instead of strict grounding.** When no chunks survive the reranker threshold,
the system answers from the model's own knowledge rather than refusing. This trades strict
"never hallucinate beyond sources" guarantees for a system that's actually useful when the
knowledge base doesn't cover a question — a deliberate product choice for a personal assistant,
not a compliance-grade RAG system.

## 4. Known Tradeoffs

**Single-machine, single-user by construction.** `USER_ID`/`DEVICE_ID` exist as columns/keys
mostly for future-proofing and namespacing (per-user ChromaDB collections, per-user SQLite
tables) — there's no auth, no multi-tenancy, no session isolation beyond what those namespaced
keys already provide. This is fine for a personal tool and would need real work (auth, request
isolation, resource limits per user) before it could serve more than one person on shared
infrastructure.

**No fine-tuned reranker or embedding model yet.** `ml/collect_pairs.py` and
`ml/finetune_embed.py` exist specifically to build toward this, but today the system runs the base
`BAAI/bge-reranker-v2-m3` and `bge-m3` checkpoints as-is. `RERANKER_MODEL_PATH` in
`config/paths.py` is dead weight *today* but deliberately kept as the landing spot for a future
checkpoint.

**The Docling OCR configuration gap** (see §2, `ingestion/pdf.py`) is a real example of design
intent (RapidOCR, as previously documented) drifting from what the code actually does (Docling's
default EasyOCR, since `ocr_options=` was never set). It works — EasyOCR is a reasonable OCR
engine — but it means the project's documented dependency/performance tradeoff never actually took
effect. This audit fixed the documentation to describe reality, but left the underlying choice
(EasyOCR vs. wiring up RapidOCR) for a human decision, since it's a real behavioral/dependency
change, not a docs bug.

**Response-shape defensive coding around Ollama's Python client** (`utils/ollama_client.py`'s
`_extract_single_embedding`/`_extract_batch_embeddings`) exists because that client's response
shapes have changed across versions before. It's more code than a single fixed-shape parser would
need, in exchange for not breaking silently on the next `ollama-python` upgrade.

**No automated test suite.** Correctness today is enforced by `ruff` (lint/format), `tsc --noEmit`
(type checking), and manual/eval-script verification (`ml/eval.py` against Weights & Biases), not
by unit or integration tests. For a portfolio project under active, single-developer iteration
this keeps velocity high, but it's the most significant thing that would need to change before
this could be maintained by more than one person or trusted without manual verification after a
refactor.

**Telemetry is best-effort and silently drops.** `telemetry.py` is fire-and-forget on a daemon
thread with no retry and no persistence of failed sends — a Pi that's offline for a day just means
a gap in the metrics, never a blocked request and never a queued backlog to replay. That's the
right tradeoff for "anonymous usage stats," and would be the wrong one for anything the product
depended on.
